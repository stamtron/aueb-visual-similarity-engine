01 · HOW TAKE-HOMES WORK

A small project, a big signal

Many data science loops include one: a short brief, a few days, a repo, then a discussion.

  • You get a deliberately vague problem and a folder of data. No one tells you which model to use.
  • You hand in code that a reviewer must be able to install and run, plus a short write-up.
  • The follow-up interview is about your decisions: why this model, how you know it works, what breaks.
  • Time-box it. A clean, honest baseline beats an unfinished clever system.

02 · THE CASE

The brief, as you receive it

You are given a folder of product images. Build two things.

1 · SEARCH

  • Given a query image (a path or a URL), return the K most similar images.
  • Each result has a score in [0, 1] and an explanation of why it matched.

2 · CLUSTERING

  • Group the folder into clusters with human-readable names.
  • Then put a new image into a cluster, or call it an outlier.

No labels are provided. No GPU is assumed. Someone else has to run your code.

03 · WHY IMAGE RETRIEVAL MATTERS

Search by picture, not by keyword

Users often cannot describe what they want, but they can show it.

CUSTOMER-FACING

  • Visual shopping: photograph a jacket, find it or similar ones (Google Lens, Pinterest Lens, ASOS Style Match).
  • "More like this": similar-item rails on product pages when an item is out of stock.
  • Real estate, travel: find listings or hotels that look like a photo you liked.

BEHIND THE SCENES

  • Duplicate listings: marketplaces catch the same item uploaded twice or re-used stolen photos.
  • Trust & safety: match uploads against known harmful or copyrighted images (e.g. PhotoDNA-style hashing).
  • Medicine, manufacturing: "show me past cases or defects that look like this one".

04 · WHY IMAGE CLUSTERING MATTERS

Find structure no one has labelled

Most image collections arrive without labels. Clustering is how you see what is in them.

ORGANISE

  • Catalogue taxonomy: a retailer onboards 50,000 supplier photos with messy or missing categories.
  • Photo libraries: group a media archive or phone gallery into themes.
  • Inspection: drone or hull-inspection images grouped by defect type (shipping, energy, infrastructure).

SPEED UP PEOPLE

  • Labelling: label one cluster at a time instead of one image at a time.
  • Data quality: spot junk, duplicates and mislabelled images before training a model.
  • New arrivals: route each new image to a team or flag it as an outlier for review.

05 · THE ASSIGNMENT, PRECISELY

Four functions are the contract

Write the interface down first. It forces the hard questions early.

# search
build_index(folder, index_path)      -> path of the written index
search(url, k, index_path)           -> [(id, score, explanation), ...]

# clustering
preprocess(folder)                   -> dataset_id
assign(url, dataset_id)             -> cluster label, or "outlier"
  • IDs come from file names (123.jpg → 123), never from list positions.
  • preprocess persists its result: the id lets you come back later without recomputing.
  • assign on the same image twice must give the same answer: idempotent.

06 · WHAT THE BRIEF LEAVES OPEN

Clarify before you code

Every one of these changes the design. Ask, or state your assumption in the README.

THE PROBLEM

  • What does similar mean: same photo? same product type? same colour or style?
  • What is a score of 0.8 supposed to mean to a user?
  • How many clusters is useful, and who reads the names?

THE CONSTRAINTS

  • Scale: 1,000 images or 10 million? That decides the index.
  • Latency and hardware: laptop CPU or GPU cluster?
  • Data quirks: duplicates, overlay text, corrupt files, mixed formats?

07 · WHAT IS BEING GRADED

Reasoning, not library knowledge

Reviewers look for evidence that you can be trusted with a real problem.

  • Runs first time: one install command, tests that pass without downloads.
  • Baseline first: pretrained embeddings + cosine before anything clever.
  • Evaluation: numbers you can re-run, even without labels.
  • Honesty: limitations and failure cases written down, not hidden.
  • Code quality: small modules, clear names, safe file handling.

08 · THE DATA

998 H&M catalogue photos

A public stand-in for a private brief: the H&M Personalized Fashion dataset on Kaggle.

  • 20 product types × 50 articles, one colour variant per product, resized to ≤ 512 px.
  • Clean studio shots on white: no overlay text, no reused photos.
  • Labels (product type, colour) exist, but the engine never sees them. They are used only to evaluate.
  • One script downloads the sample. The images are never committed: competition rules.

09 · ARCHITECTURE

One path for every image

Indexing, querying, clustering and assignment all decode and embed the same way.

folder or URL→load_image()→embed()
CLIP or DINOv2→index.npz/clusters
  • Two preprocessing paths (one for the index, one for queries) is the classic train/serve skew bug.
  • Everything on disk is .npz + JSON: no pickle, so loading a file cannot run code.
  • Writes go to a temp file, then rename: a crash never leaves a half-written index.
  • Heavy optional parts (OCR, plotting) are imported only when used.

10 · SEARCH

Embeddings + brute-force cosine

Represent each image as a vector; the nearest vectors are the most similar images.

  • CLIP ViT-B/32 turns each image into 512 numbers, normalised to length 1.
  • A query is one matrix-vector product: 8–21 µs over 998 images on a CPU.
  • No vector database: below about 10⁵ images it adds a service and buys nothing.
  • Embedding the whole folder takes about 8 s on a laptop.

11 · THE SCORE

Raw cosine is not a score

The brief asks for [0, 1]. Cosine is technically in range, but it does not mean anything to a user.

CLIP on H&Mcosine
random noise vs. its nearest catalogue image0.67
2nd percentile of real nearest-neighbour pairs0.79
median nearest-neighbour pair0.93
  • Calibrate per index: score = share of the catalogue's real neighbour pairs below this cosine.
  • 0.9 now means "closer than 90% of real pairs". The ranking never changes.
  • Below the 2nd percentile, the query is flagged as out of distribution.

13 · CLUSTERING

Choose K by stability

k-means on the same embeddings, for K = 4…12, five random seeds each.

  • Silhouette is low and flat on product photos (0.11–0.15): "maximise silhouette" picks noise.
  • Better question: would a colleague who re-ran this get the same clusters? Measure seed-to-seed agreement (ARI).
  • Rule: among K with ARI ≥ 0.8, take the best silhouette; otherwise the most stable K.
  • On H&M no K reaches 0.8. With 996 images the fallback picks K = 7; with 998 it picks K = 9.
  • That is a finding: 20 product types do not form 20 clean groups.
THE K TABLE IS SAVED, SO THE CHOICE IS AUDITABLE
AUEB · MSc Data Science · the interview example14 / 24
14 · NAMES AND NEW IMAGES

Name by lift, assign by neighbours

NAMING A CLUSTER

  • Format with the highest mean tag probability.
  • Garments with the biggest lift: cluster mean minus dataset mean.
  • Without lift, "dress" would name every cluster.
  • e.g. studio product photo: sneakers

ASSIGNING AN IMAGE

  • Same bytes seen before? Return the stored answer.
  • Best cosine below the 2nd-percentile threshold → outlier.
  • Else the cluster with the best mean of its top-3 members.
  • Append to additions.jsonl; later images see it.

15 · EVALUATION WITHOUT LABELS

Build tests where you know the answer

No labels? Create queries whose right answer you know.

  • Augmentation recall: greyscale, downscale, JPEG q10, mirror, crop. The original must come back first.
  • The banner trap: stamp a red "SALE -50%" strip on 50 products as distractors, query with 50 others wearing it. Does the text beat the product?
  • Near-duplicates (pHash): on H&M it chains 805 white-background shots into 20 fake groups, so the script reports n/a.
  • Sanity: noise, a blue square and black text on white must be flagged as outliers.

17 · THE INTERESTING PART

CLIP reads text

It was trained on image–caption pairs. On catalogues with banners, it matches the banner.

ON THE ORIGINAL CATALOGUE

  • 485 images, many with real overlay text.
  • Same photo, different banner: CLIP found the pair only 44% of the time.
  • OCR + inpainting the text before embedding: 85%.
  • DINOv2, no OCR at all: 85%.

REPRODUCED ON H&M

  • No real text, so we add a synthetic banner.
  • A bannered stranger beats the real match in 10% of CLIP queries.
  • Masking: 4%. DINOv2: 0%.
  • Masking is ~13× slower and turns inpainted junk into a "white studio shot".

18 · DECISIONS

Why CLIP is still the default

Winning one metric is not the same as being the right choice.

  • CLIP's zero-shot tags power the explanations and the cluster names, with no second model.
  • It groups better by colour, which shoppers often care about.
  • DINOv2 is one flag away: vsim index … --model dinov2-s14.
  • Text masking stays as an option for catalogues that really have banners; the cost is written down.
  • Every trade-off lives in docs/decisions.md, so a reviewer can disagree with a reason, not a guess.

19 · ENGINEERING

Small things reviewers notice

  • uv sync → pytest passes in ~2 s: a fake embedder, no network, no model download.
  • Bug fixes come with a test that fails before the fix.
  • Index metadata (model, options, tag vocabulary) travels with the index; an old index fails loudly.
  • The dataset id is a content hash: change one pixel, get a new id. Stale results are never reused.
  • No pickle, atomic writes, duplicate IDs are an error.

21 · WHAT WE DID NOT DO

Limitations are part of the answer

Say what you would do next, and why you did not do it yet.

  • Human relevance judgements: a few hundred graded query–result pairs. The gold standard.
  • Online metrics: click-through and add-to-cart would replace all of the offline numbers.
  • Scale: 998 vectors say nothing about 10 M. Then: an ANN index, sharding, batch embedding.
  • Clustering in production: re-cluster when additions pass ~10–20%; let curators rename clusters.
  • Calibration UX: a good match can score 0.09 on a tight catalogue. Honest, but it reads as pessimistic.

23 · TAKEAWAYS

Build it so someone else can trust it

The model was the easy part.

  • Turn a vague brief into a written contract and stated assumptions.
  • Start with a pretrained baseline; spend the time on evaluation.
  • Invent tests with known answers when you have no labels.
  • Find one real failure, measure it, and compare fixes on cost as well as accuracy.
  • Try it: github.com/stamtron/aueb-visual-similarity-engine, then follow docs/getting-started.md.
